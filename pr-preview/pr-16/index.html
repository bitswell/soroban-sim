01

Core wasm speaks only numbers

A raw wasm module's imports and exports pass numeric values — i32, i64, f32, f64. No strings, no records, no lists. Anything richer has to be hand-marshalled through linear memory by both sides, with both sides agreeing on the layout by convention.

02

The Canonical ABI does the marshalling

A component wraps core wasm in a typed interface described in WIT. The Canonical ABI pins down the layout: here, each XDR list<u8> crosses as (ptr, len) — one cabi_realloc into guest memory plus one memcpy — the request record flattens to an 88-byte struct, and the outcome variant lifts back as a discriminant byte plus payload, copied out before a post-return free.

03

jco transpiles it to JS

jco transpile splits the 3.1 MB component into its core .wasm plus ~227 KB of generated glue that implements the Canonical ABI in JavaScript. Its 15 WASI 0.2 imports (stdio, clocks, seed) come from preview2-shim — yet a whole successful run calls exactly one: insecure-seed, once. Cold start ~23 ms; a warm call ~0.2 ms; memory flat at 2.25 MiB.

04

How soroban-sim uses it

World simulator exports simulate, simulate-transaction, simulate-trace and a run-fixture self-test; each simulate call returns complete(ssim) or needs-state(keys) — and holds no state between calls: every round re-sends the whole snapshot, then reruns deterministically. The Soroban contracts stay plain core wasm, not baked in: their bytes arrive as ContractCode ledger entries through that loop (or uploaded here), interpreted by the embedded host.
